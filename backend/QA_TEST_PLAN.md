# QA Test Plan

## Цель

Зафиксировать минимальный набор проверок для новых изменений в VELTARQ и единый формат описания найденных дефектов.

## Что проверять для каждого изменения

- Основной пользовательский сценарий: действие выполняется, результат соответствует требованиям.
- Негативные сценарии: пустые, неверные и граничные значения обрабатываются корректно.
- Интерфейс: элементы отображаются, доступны и не перекрывают друг друга на поддерживаемых разрешениях.
- API и интеграции: корректны статус-коды, тело ответа и обработка ошибок на клиенте.
- Регрессия: связанные пользовательские сценарии продолжают работать после изменения.
- Браузеры: проверка в актуальных Chrome и Edge, если изменение затрагивает web-интерфейс.

## Условия перед тестированием

- Доступна тестовая сборка или воспроизводимый способ запустить изменение.
- Требования, макеты или ожидаемое поведение согласованы с командой.
- Есть необходимые тестовые учётные записи и данные.
- Версия сборки и окружение зафиксированы в результате проверки.

## Критерии готовности к релизу

- Выполнены основные и негативные сценарии затронутой функциональности.
- Критические и блокирующие дефекты отсутствуют.
- Известные ограничения и непроверенные риски задокументированы.
- Исправленные дефекты прошли повторную проверку и регрессию.

## Шаблон баг-репорта

```text
Заголовок: [Компонент] Краткое описание проблемы

Окружение: версия сборки, ОС, браузер/устройство
Предусловия: что должно быть подготовлено
Шаги воспроизведения:
1. ...
2. ...

Фактический результат: ...
Ожидаемый результат: ...
Severity: Blocker / Critical / Major / Minor / Trivial
Priority: High / Medium / Low
Вложения: скриншот, видео, логи или ответ API
```

## Результат проверки

Для каждой задачи фиксируется один из статусов: `Passed`, `Failed`, `Blocked` или `Not tested`, а также ссылка на задачу, дефект или доказательство проверки.
